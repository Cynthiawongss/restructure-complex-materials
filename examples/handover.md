# 案例：把项目交接资料变成可接手的结构

[返回首页](../README.md) · [English](handover.en.md)

这是虚构产品演示工具案例，姓名、项目和 .invalid 网址均不对应真实资料。

## 处理前

收到 A–F 六段资料、39 个字段。原输入没有实体分类键，也没有预先合并的答案。

| 来源 | 原材料中的困惑 |
|---|---|
| A 工作表 | 原型 ClipDeck、预算 400 美元、技术栈、负责人、联系人和长操作说明 |
| B 交接消息 | 相同网址，预算 650 美元；新增审批人、上传限制和多窗口待决事项 |
| C 外部案例 | 也叫 ClipDeck，但仓库不同，声称已上线 |
| D 运维说明 | 对内部仓库有明确关联，保留排错步骤和失败样片规则 |
| E 参考清单 | 关联项目未指定，代码 X7 未解释，有完整操作顺序 |
| F 复制索引 | 重复 A 的名称、网址、状态和负责人 |

[完整原始材料](../validation/inputs/handover.zh-CN.md)

## 处理后：主视图、详情、追溯分别承担不同任务

| 层次 | 放什么 | 为什么 |
|---|---|---|
| 默认用途总览 | 阅读名称、用途、资料性质、关键限制、详情入口 | 先找到该看哪条 |
| 详情 | 技术、输出、不同人员角色、预算记录、完整说明与相关资料 | 找到后能执行和比较 |
| 来源台账 | 原字段、原值、出处、新位置、处理方式 | 核对没有遗漏或误合并 |

这不是强制所有用户都用三张表；它们可以是同一资料库的视图与详情，也可以是一个文档中的不同章节。

## 几个重要决定

- A、B、F 依据相同名称和网址合并阅读入口；保留各自原字段与来源。
- C 的网址、性质不同，与内部同名项目分开。
- “技术栈／技术”可以统一为属性；负责人 Lin、联系人 Mei、审批人 Arun 分别保留。
- 400 与 650 美元同时保留，版本先后未知，不取平均、不擅自选一个。
- 原录制留存到 MP4 审阅通过，与失败样片留存到问题关闭，是两条不同规则，均保留。
- E 保持未指定关联，X7 保持未知；不按主题相似就编出项目关系。
- 原材料不修改、来源不删除；本例仅交付方案。

## 完整结果

[中文独立试用交付](../validation/runs/chinese.md)包含可点击的默认总览、四条详情、字段字典，以及逐项对应的 **39 个来源字段**。表格摘要没有替代长说明原文。

[英文独立试用交付](../validation/runs/english.md)使用不同阅读编号，但保留相同源信息和关系边界。两种结果的文字和排版不要求完全一致。
